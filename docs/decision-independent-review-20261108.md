# 낮은 확신도 판정의 독립 검토

## 원인과 최소 변경

기존 실제 35개 검사에서는 마지막 SQLite → PostgreSQL 변경이 `충돌`, confidence 0.21로 반복 응답돼 34/35에서 멈췄다. DB 진행 저장 문제가 아니라 모델 판정의 보류였다. 결정자 정보 표기만 분리하면 이 사례가 `변경` 0.67로 바뀌었지만, 전체 요청에 적용하자 기존 회귀에서 새 오판과 보류가 발생했다. 질문 축약·단계 분리·선택지 축소·원문 발췌도 단독 해결책으로 채택하지 않았다. 이는 입력 형식에 민감함을 보여 주며 모델 내부 원인까지 입증하지는 않는다.

최종 구현은 기존 확신도 충분한 경로를 유지한다. Decisions가 0.6 미만인 쌍만 기존 추론 모델이 원문을 독립 검토한다. 검토가 0.6 이상이면 기존 카드의 결정자 정보만 명시한 입력으로 Decisions를 한 번 재확인한다. 검토 결과 자체는 Decisions에 보내지 않는다. 두 판정이 모두 0.6 이상이며 라벨이 일치해야 성공한다. 최종 확신도는 두 값의 최솟값이다. 기준 완화·규칙 대체·반복 샘플링은 없다.

불일치·검토 실패·불충분한 확신도는 계속 미완료로 남는다. 무효 응답/거절은 이 검토 경로를 시작하지 않는다. 일반 ‘사용자’/‘미상’ 표기는 같은 사람이라고 추정하지 않는다. 원문은 기존 마스킹 경로를 통과한다. 결과에는 `reviewedBy`, 진단에는 두 사용 방법을 기록한다. 추가 호출은 불확실한 쌍마다 최대 추론 모델 1회 + Decisions 1회다.

## 실제 API 검증

| 묶음 | 이전 완료 | 개선 후 완료 | 개선 후 잘못된 완료 |
|---|---:|---:|---:|
| 기존 회귀 42회 | 33 | 36 | 0 |
| 범위/최종값 회귀 38회 | 30 | 32 | 0 |
| 추가 회귀 16회 | 10 | 10 | 0 |
| 원래 실패 + 신규 사례 12회 | 별도 비교 | 12 | 0 |

기존 96회 중 완료 73→78, 기존 완료 사례 퇴행 0, 완료된 240개 쌍의 오판 0. 나머지 18회는 보류이며 성공으로 계산하지 않았다. 원래 실패 사례는 두 번 모두 `변경`, 최종 confidence 0.67로 완료했다. 이 평가는 반복 합성 사례이며 일반 정확도의 보장은 아니다.

실제 PostgreSQL 17.9 + API 프로세스 + 실제 Decisions/Responses: 7개 커밋 후 강제 종료, 재시작 후 35/35 완료, 완료된 쌍 재호출 없음, 마지막 변경 경고 저장. 요청 38회(중단 중 미커밋 요청 1회 중복 포함), 18.227초, 추정 $0.0036886. crash lease를 임시 DB에서 만료시켰으므로 운영에서의 3분 대기시간은 이 수치에 포함되지 않는다. 테스트 계정 간 격리도 확인했다.

원래/신규 12회와 기존 96회의 추정 비용은 $0.04718865, API 호출 334회다. 실제 응답 usage 기준이며 계정 청구서, 세금, 호스팅은 포함하지 않는다. Decisions는 [공식 요금](https://developers.openai.com/api/docs/guides/decisions#pricing-and-availability), 추론 모델은 [공식 모델 요금](https://developers.openai.com/api/docs/pricing) 적용.

DB 진행 저장/복구/마이그레이션/권한과 클라우드 HTTP 경계 회귀 10개 통과. AI 테스트 최종 결과는 배포 기록에 함께 보관한다. 초기 테스트 한 건은 의도된 독립 검토 HTTP 호출 추가를 반영하도록 기대 경로를 수정했고, 잘못된 검토 응답은 여전히 실패함을 확인했다.

## 증거 위치와 배포 범위

작업 폴더 `work/decision-review-{target,regression,fresh,additional}-20261108/`의 fixtures/requests/runs/summary 파일과 `work/resumable-live-evidence-20261108-reviewed/`에 합성 입력·실제 응답·비용·진행 결과가 있다. 원래 실패·폐기한 실험도 별도 폴더에 보존했다. 실제 credential 값은 어떤 증거에도 포함하지 않는다.

마지막 owner-placeholder 공백 처리 보완은 동일 판정 사례의 의미를 바꾸지 않으며 별도 단위 검증했다. 제품 threshold, 원래 질문/선택지, 후보 누락 방지, 승인·마스킹·팀 격리 정책은 유지한다. 새 정책 해시가 진행 중 작업의 이전 체크포인트를 무효화하는 기존 동작도 유지한다.

운영 적용은 별도 단계다. `conflict_checks.progress` 추가, 기존 프로젝트 키의 운영 비밀 설정, 소스 allowlist 배포 및 HTTPS 검증을 수행해야 한다. backend 이력은 통합하지 않는다. 검토 모델이 없으면 종전처럼 낮은 확신도를 보류한다.
