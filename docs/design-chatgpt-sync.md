# ChatGPT 계정 동기화 설계 (3층 수집)

상태: 3판 · 2026-11-13 · 작성 김동균(Claude와 함께)
- 반박 검토 1회 반영(부록 A)
- ChatGPT 내부 API 사실 조사 반영(부록 B). 2차 자료라 10장 관문으로 확인한다.

코드 줄 번호는 `~/syncup-demo`(커밋 `27a0474`, 확장 0.2.2) 기준으로 썼다. **구현 기준은 확장 0.2.7(`6342111`, 브랜치 `claude/slop-fixes-20261112` = `claude/murex-default`)이다**(17장).
0.2.7에서는 폴더가 바뀌었다.
- 루트의 수집기 `*.py` → `collector/*.py` (`turn_intake.py`는 내용이 같고 위치만 옮김)
- `src/` → `scanner/src/`
- `check_*.py` → `checks/`

확장의 `lib/sites/chatgpt.ts`와 `lib/auto-collect.ts`는 0.2.7에서 바뀌어 줄 번호가 다르다.

## 1. 목표와 범위

ChatGPT 웹에서 보이는 대화 가운데 **수집 기간 안에, 동기화를 켠 뒤에 새로 생긴 메시지만**, 최대한 실시간에 가깝게 로컬 수집기로 보낸다. 웹 탭에서 한 대화와 휴대폰·데스크톱 앱에서 한 대화 모두 대상이다. 같은 계정 기록에 쌓이고, 목록에 `conversation_origin` 필드가 있다는 것이 간접 근거다(부록 B).

| 목표 | 기준 |
|---|---|
| 웹 탭 대화 | 답변이 끝나고 몇 초 안 (지금 화면 경로 그대로) |
| 앱·다른 기기 대화 | 활발할 때 1~2분 안, 조용할 때 5분 안 |
| Chrome이 꺼졌다 켜짐 | 켜지고 chatgpt.com 탭이 열린 뒤 첫 확인에서 빠진 구간을 따라잡음 |
| 지금 경로 | 그대로 쓴다. 동기화가 꺼져 있거나 고장 나면 지금과 똑같이 동작 |

범위 밖:
- 임시 채팅: 목록에 없다.
- 팀 워크스페이스 계정: `Chatgpt-Account-Id` 헤더가 필요하다. 첫 판은 개인 계정만 다룬다.
- Chrome이 꺼져 있는 동안의 수집: 불가능하다.
- 종료 시각 뒤의 따라잡기: 원칙상 하지 않는다.
- 서버가 밀어 주는 WebSocket 듣기: 2차로 미룬다(3장).

## 2. 지켜야 할 원칙 (CLAUDE.md 9장 · 팀 고정 규칙)

- **설정한 기간만.** 보낸 시각이 아니라 ChatGPT에서 **만들어진 시각**으로 판단한다. 기간은 "동기화 창"이다(4장): 수집 기간 안, 동기화를 켜 둔 구간 안(동의 이후), 일시정지 구간 밖.
- **기간 밖 본문은 탭 밖으로 나가지 않는다.** 탭이 동기화 창으로 먼저 거르고, 수집기가 한 번 더 판단한다.
- **종료 시각 뒤에는 아무것도 보내지 않는다.** 그때는 수집기가 `turns.append`를 거절한다(`collection_session.py:65`). 동기화도 그 시각에 멈춘다.
- **승인한 것만 팀에.** 분류·승인 절차는 그대로다. 동기화는 `turns.append` 앞단만 더한다.
- **동의.** 수집 범위가 "탭에서 본 대화"에서 "동기화 창 안의 계정 대화 전체(앱·프로젝트 포함)"로 넓어진다. 그래서 별도 스위치를 두고 기본은 꺼 둔다. 동의 문구에 넣을 것:
  - 앱 대화도 포함된다
  - 임시 채팅은 제외된다
  - 분류용 발췌가 외부 AI로 간다
  - ChatGPT에서 대화를 지워도 이미 모은 것은 지워지지 않는다
- **팀 고정 규칙.** `lib/sites/chatgpt.ts`(화면 감지 규칙)와 `lib/auto-collect.ts`(디바운스 2초·재시도)는 고치지 않는다. 30초 상태 새로 고침 알람의 주기도 그대로다.
- **비밀값.** ChatGPT 세션 토큰은 탭 메모리에만 둔다. 계정 id는 해시로만 저장한다.

## 3. 전체 구조

```
 chatgpt.com 탭 (사용자가 연 탭)
 ├ auto-collect (그대로) ─ collect ─────────────────────────────▶ background ─▶ appendTurns ─▶ 수집기
 └ chatgpt-api 클라이언트 (새, 격리 world, 같은 출처 fetch)            │
      ▲  sync.page / sync.conversation                               │
      └──────────────────────────── 동기화 패스 (새, background) ◀────┘ 방아쇠: touch · 알람 · 시작
                                     커서까지 목록을 거슬러 확인 → 바뀐 대화만 열기 → 새 턴만 보냄
```

세 층은 방아쇠만 다르고 **같은 "동기화 패스" 하나**를 쓴다.

| 층 | 방아쇠 | 하는 일 |
|---|---|---|
| 1층 웹 탭 | 화면 경로의 `collect` 요청(touch) | 지금처럼 화면 메시지를 보낸다. 5초 뒤 패스를 한 번 돌려 화면이 기준선 때문에 안 보낸 턴을 채운다 |
| 2층 앱·다른 기기 | 알람(활발·조용) | 패스가 커서 이후에 바뀐 대화를 찾는다 |
| 3층 따라잡기 | 브라우저 시작, 동기화 켬, 잠자기에서 깨어남 | 같은 패스. 커서가 오래돼 더 멀리 거슬러 갈 뿐이다. 잠자기 동안 놓친 알람은 깨어날 때 한 번 울린다(alarms 문서) |

### 동기화 패스

1. **기본 목록.** 탭에 `sync.page`를 보내 `/backend-api/conversations?offset=…&limit=28&order=updated`를 받는다. 웹 앱이 스스로 쓰는 인자와 같게 둔다(부록 B). 탭은 `{id, updateTime, isArchived, gizmoId}`만 돌려준다. 제목은 돌려주지 않는다.
2. **프로젝트 목록.** 프로젝트 대화는 별도 엔드포인트다(`/backend-api/gizmos/snorlax/sidebar`, `/backend-api/gizmos/{gizmo}/conversations?cursor=`).
   - 프로젝트 목록은 조용 주기 패스와 3층 패스에서만 읽는다. 활발 주기에서는 이미 아는 활성 프로젝트만 본다.
   - 기본 목록에 프로젝트 대화가 같이 나오면(P1) 이 단계를 뺀다.
3. **처리 대상.** `updateTime`이 **커서**보다 새로운 대화를 대상에 넣는다. 커서보다 오래된 항목이 나오면 그 목록의 다음 쪽은 읽지 않는다.
   - 커서 = max(동기화 창 시작, 마지막 완료 패스 시작 − 여유 10분)
   - 보관한 대화는 뺀다.
   - 같은 id는 한 번만 넣는다.
4. **대화 상세.** 대상 대화마다 `sync.conversation(id, windows)`를 보낸다. 탭은 상세를 받아 6장 규칙으로 정규화한다. 그리고 동기화 창 안의 완료된 턴만 돌려준다.
5. **보내기.** 돌려받은 턴을 `appendTurns`로 200개씩 나눠 보낸다.
6. **커서.** 모든 대상을 끝내면 커서를 패스 시작 시각으로 올린다. 다음 경우에는 올리지 않고 다음 패스에서 다시 본다.
   - 생성 중인 답변이 있는 대화가 있을 때
   - 실패한 대화가 있을 때
7. **속도.** 한 패스는 상세 최대 20건이다. 상세 요청 사이에는 1~2초를 무작위로 둔다(공개 도구들과 같은 수준). 남은 대상은 다음 알람에서 이어 간다.

### 주기

- **활발** 2분(관문 P5를 통과하면 1분): 최근 10분 안에 touch가 있었거나 패스가 새 턴을 찾았을 때. 휴대폰으로 대화하는 중인 경우다.
- **조용** 5분.
- **쉼**: 429를 받으면 `Retry-After`를 따르고, 없으면 30분 쉰다. 거듭되면 두 배로 늘린다(최대 2시간). 403·봇 확인 화면은 바로 2시간 쉰다.
  - 목록 429는 몇 시간 이어지고 사용자 본인 ChatGPT의 대화 목록도 막는다는 보고가 있다. 그래서 목록 요청은 아껴 쓴다.
- **멈춤**: 수집 일시정지·종료, 동기화 꺼짐, ChatGPT 로그아웃, 계정 불일치, 고장 표시, 응답할 chatgpt.com 탭 없음.

알람 이름은 `chatgpt-sync`다.
- 지금 `onAlarm` 리스너는 이름을 보지 않으므로(`background.ts:75`) 이름으로 나눈다. `refresh` 30초 주기는 그대로 둔다.
- 알람은 서비스 워커가 시작할 때마다 있는지 확인하고 다시 만든다. `persistAcrossSessions`는 Chrome 150부터라서다.

**서버 신호(2차).** chatgpt.com은 `wss://ws.chatgpt.com/…` WebSocket을 쓴다(`/backend-api/celsius/ws/user`). 다른 기기 변경이 이 소켓으로 오는지와 이벤트 모양은 미확인이다. 격리 world 콘텐츠 스크립트는 페이지 소켓을 들을 수 없고 MAIN world 스크립트가 필요하다. 그래서 첫 판은 폴링만 한다. P4에서 신호가 확인되면 "활발" 방아쇠로 붙인다.

## 4. 동기화 창

수집기가 계산해 상태로 내보낸다. 탭과 수집기는 같은 값으로 판단한다.

```
동기화 창 = 수집 기간 [세션 시작, 종료 시각)
          ∩ 동기화를 켜 둔 구간들 (켬 = 동의 시각)
          − 일시정지 구간들 (종료 뒤 연장한 사이도 일시정지로 기록됨, collection_settings.py:68-77)
```

- **세션 시작은 상태 폴더당 한 번 정해진다**(`app.py:108`).
- **기간 전체는 24시간보다 길 수 있다.** 종료 시각은 "지금부터 24시간 안"으로만 늘릴 수 있다(`collection_settings.py:72`). 하지만 여러 번 늘릴 수 있어서다. 그래서 따라잡기 하한은 "24시간 전"이 아니라 동기화 창 시작이다.
- **켜기 전과 꺼 둔 동안의 대화는 들어오지 않는다.** 처음 켤 때 과거 대화가 쏟아지지 않는다.
- **턴 단위로 판단한다.** 질문과 그 답변을 한 턴으로 본다. 턴 안 메시지의 가장 이른 시각부터 가장 늦은 시각까지가 창 안이어야 보낸다. Rust 스캐너와 같은 규칙이다(`src/review_db.rs:89-91` `within_window`).
  - 사용자 메시지 시각이 답변보다 늦게 찍히는 경우가 있다는 보고가 있다(부록 B). 메시지 단위로 판단하면 경계에서 한쪽만 빠진다.

## 5. 탭 전송 계층

동기화 요청은 chatgpt.com 탭의 콘텐츠 스크립트(격리 world)가 같은 출처 fetch로 보낸다.

- 콘텐츠 스크립트의 요청은 Chrome 85부터 페이지와 같은 규칙을 따른다(Chromium 문서). 같은 출처 요청에 쿠키가 실리는 것은 표준 동작으로 본다(추론, P2에서 확인). **새 권한이 필요 없다.**
- background에서 직접 부르는 방식은 쓰지 않는다. `host_permissions`가 필요하고 쿠키가 실리는지 미확인이라서다.

**대표 탭.**
- 콘텐츠 스크립트가 응답하는 chatgpt.com 탭 가운데 활성 탭을, 없으면 마지막으로 응답한 탭을 고른다.
- 한 패스는 한 탭에서만 돈다.
- 얼린 탭(Chrome 132부터)과 폐기된 탭은 응답하지 않는다. 그때는 다른 탭을 고르거나 이번 주기를 건너뛴다.
- **최소판은 사용자가 연 탭만 쓴다.** 탭이 없으면 "멈춤"이고, 팝업에 "chatgpt.com 탭을 하나 열어 두면 앱 대화도 가져와요"를 띄운다.
- 고정 동반 탭은 2차로 미룬다. Chrome을 다시 켤 때 새 id로 로드되지 않은 채 복원되고, 창을 닫을 때도 `onRemoved`가 오는 문제가 있다.

**탭과의 메시지.**
- `sendResponse` 방식으로 답한다(Chrome 148 미만 호환, `ai-chat.content.ts`의 ping과 같은 모양).
- background는 요청마다 20초 시간 제한을 둔다.
- 다음 경우는 "일시 오류"로 보고 다음 주기에 다시 한다: 답이 없음, 채널이 닫힘(페이지 이동, 확장을 다시 불러온 뒤 남은 옛 스크립트).

**인증.**
- 탭 클라이언트가 `GET /api/auth/session`의 `accessToken`을 메모리에 두고, 읽기 요청에 `Authorization: Bearer`를 붙인다(공개 도구들과 같음).
  - 공개 도구들은 읽기에 `oai-device-id`나 sentinel 토큰을 쓰지 않는다. 페이지가 붙이는 헤더는 P2에서 확인한다.
  - 401이면 토큰을 한 번 다시 받는다. 세션 응답의 `expires`가 지나면 새로 받는다.
- 세션 응답의 사용자 식별자를 해시해 응답마다 background에 넘긴다(P6에서 필드 확인).
  - 동기화를 켤 때 수집기에 묶은 계정 해시와 다르면 멈춘다.
  - 수집기도 `turns.append`의 계정 해시를 확인한다(C7). Chrome 프로필이 여럿이면 다른 계정이 같은 수집기에 넣는 것을 막는다.

**탭이 돌려주는 것.** 원본 JSON은 탭 밖으로 내보내지 않는다.
- 목록: `{id, updateTime, isArchived, gizmoId}`
- 대화: 동기화 창 안의 완료된 턴의 메시지와 `inProgress`

## 6. 메시지 정규화

ChatGPT 내보내기 파일도 같은 `mapping`/`current_node` 구조다. 웹 내보내기 파서(`web/src/lib/chatgpt-export.ts:33-66`)와 공개 도구(chatgpt-exporter)의 규칙을 합쳐 `shared/`에 공용 파서를 두고, 탭 클라이언트와 웹이 같이 쓴다(웹 담당과 조율).

**가지.** `current_node`에서 `parent`를 따라 올라가 뒤집는다. `current_node`가 없으면 자식이 없는 노드를 끝점으로 쓴다.

**빼는 메시지.**
- 역할이 `system`·`tool`인 것
- `recipient`가 null도 `all`도 아닌 것(도구에 보내는 말)
- `content_type`이 `code`, `execution_output`, `tether_*`, `user_editable_context`, `model_editable_context`, `thoughts`, `reasoning_recap`인 것
- `metadata.is_visually_hidden_from_conversation`, `metadata.is_thinking_preamble_message`가 참인 것
- 본문이 공백뿐인 assistant 메시지

**본문.**
- `text`는 `parts`를 잇는다.
- `multimodal_text`는 문자열 part와 음성 전사(`audio_transcription`)만 쓰고, 이미지·파일은 "[첨부 N개]"로 적는다.
- 위젯 답변은 `metadata.model_dil_v2.fallbackMarkdown`을 쓴다.
- 인용 표시 문자열(`content_references[].matched_text`)은 지운다.

**완료.**
- 마지막 assistant 메시지의 완료 여부는 `metadata.is_complete`, `metadata.finish_details.type`, `status`, `end_turn`으로 판단한다. 정확한 값은 P7에서 확인한다.
- 생성 중이면 그 턴을 보내지 않고 `inProgress`를 표시한다.
- `finish_details.type == 'interrupted'`(사용자가 멈춤)는 완료로 본다.

**시각.** 상세의 `create_time`은 유닉스 초(소수)다. 목록의 `update_time`은 ISO 문자열이라 둘 다 처리한다. `create_time`이 없는 메시지가 있는 턴은 보내지 않는다(기간 판단 불가).

**합치지 않는다.** 한 답변이 assistant 노드 여러 개로 나뉠 수 있다. 공개 도구는 이를 합치지만, 우리는 노드마다 한 메시지로 보낸다. 이유는 둘이다.
- 메시지 id를 ChatGPT 노드 id와 1:1로 두어야 화면 경로와 id를 맞출 수 있다.
- 한 턴에 assistant 메시지가 여러 개여도 묶음은 한 턴으로 묶는다(`ai/syncup_ai/batch.py:14-21`).

**보내는 `CollectedMessage`.**

| 필드 | 값 |
|---|---|
| `id` | `chatgpt:<message.id>`. 화면 경로의 `data-message-id`와 같은 값으로 보인다(부록 B, P3) |
| `site` | `chatgpt` |
| `conversationId` | 대화 id |
| `role`, `text` | 위 규칙대로 |
| `createdAt` (새) | `create_time`(ISO) |
| `origin` (새) | `sync` |
| `turnId` (새, 스캐너 경로가 이미 쓰는 필드) | 그 턴의 사용자 메시지 id. 같은 `turnId`끼리 한 턴으로 묶인다(`batch.py:19-20`). 도착 순서와 상관없이 질문·답변 짝이 맞는다 |
| `collectedAt` | 보낸 시각 |

## 7. 중복과 순서

**왜 문제인가.**
- 수집기는 (팀, 세션, site, 대화, 메시지 id)로 중복을 막는다(`turn_intake.py:42-43`).
- 그런데 같은 id인데 본문·화자가 다르면 `message_changed`로 격리한다(`turn_intake.py:56-63`).
- 화면 경로 본문은 렌더된 글이고 동기화 본문은 마크다운 원문이라 거의 항상 다르다.
- 화면 경로의 `turn-attr` 전략은 턴 안의 **첫** `data-message-id` 하나만 쓴다(`chatgpt.ts:134`). 그래서 화면 메시지 id가 동기화가 보내는 assistant 노드 id와 다를 수 있다. 예: 첫 노드가 생각 머리말이면 동기화는 그 노드를 빼고 본답변 노드를 보낸다.

**규칙.**
- **C4-a 같은 id, 다른 origin = 중복.** 격리하지 않고 중복으로 센다. 먼저 저장된 본문이 남는다.
  - origin이 없는 옛 메시지는 `screen`으로 본다.
  - 같은 origin에서 본문이 다르면 지금처럼 격리한다(변조 감지 유지).
  - 비교는 가린 뒤의 본문끼리 한다(`turn_intake.py:72`).
- **C4-b 화면이 이미 받은 턴은 건너뛴다.** 동기화 턴의 사용자 메시지 id가 화면 경로로 이미 들어와 있고, 그 대화에 그 질문 뒤 화면 경로의 assistant 메시지가 있으면 그 턴 전체를 받지 않는다.
  - 화면이 질문만 받고 답을 놓친 경우(답변 중 탭을 닫음)에는 동기화가 그 턴을 받는다. 이때 답변만 받는다. 질문은 C4-a로 중복이다.
- **C4-c 시각 채우기.** 화면 경로 행이 아직 묶이지 않았으면, 동기화가 본 같은 id의 `createdAt`을 그 행에 채운다. 본문은 바꾸지 않는다.
- **C5 정렬(권장).** 묶을 때 대화 안을 시각 순으로 정렬한다.
  - 기준은 `createdAt`(날짜로 해석), 없으면 `collectedAt`이고, 같으면 rowid로 정한다.
  - 늦게 온 앞쪽 턴이 뒤에 붙는 것을 막는다.
  - C4-c 덕분에 화면 경로 행도 서버 시각 기준으로 맞춰진다. 이미 묶인 행은 다시 묶지 않는다.

**남는 중복.**
- **해시 id.** 화면에 `data-message-id`가 없으면 화면 경로는 해시 id를 쓴다(`chatgpt.ts:136`). 이때 C4-a는 못 거른다. 하지만 사용자 메시지 해시 id는 동기화 id와 다르므로 C4-b도 못 거르고 두 번 분류된다. 지금 ChatGPT 화면은 대부분 id가 있어 드물다(P3). 화면 경로에서 해시 id를 거르는 방법은 쓰지 않는다. 거른 메시지도 auto-collect가 보낸 것으로 표시해(`auto-collect.ts:54`) 동기화가 놓치면 사라지기 때문이다.
- **내보내기 zip.** zip은 `site: chatgpt-export`이고 id에 접두사가 없어(`collector-intake.ts:12-15`) 같은 구간을 넣으면 두 번 분류된다. 3층 안내에 "동기화가 켜져 있던 구간은 zip으로 넣지 마세요"를 적는다.

## 12. 위험

- **이용약관.** OpenAI 약관은 데이터·출력을 자동·프로그램 방식으로 추출하는 것을 금지한다(2024-12판 미러로 확인, 현재판 원문 미확인). 동기화 패스는 여기에 직접 해당한다. 탭 안 같은 출처 요청은 봇 차단에 걸릴 가능성을 낮출 뿐 이 조항에서 벗어나게 해 주지는 않는다. 본인 계정, 읽기만, 시간당 수십 회 이하로 줄였지만 위험이 없어지지 않는다. 시연 전용(기본 꺼짐)으로 둘지 정한다(15장).
- **비공식 API.** 공개 문서가 없고 근거는 모두 2차 자료다. 예고 없이 바뀔 수 있고(P9), 바뀌면 "고장"으로 멈추고 화면 경로로 돌아간다.
- **사용자 서비스 영향.** 목록 429는 사용자 본인의 ChatGPT 화면에도 영향을 준다. 주기를 보수적으로 잡고 P5로 확인한다.
- **수집 범위 확대.** 동기화 창 안의 개인 대화도 들어와 분류용 발췌가 외부 AI로 간다. 별도 동의와 로컬 가림·개인 분류로 줄인다. 대화별 제외 기능은 없고, 이번 범위에도 넣지 않는다.
- **팀 고정 규칙.** 감지 규칙·타이머 파일은 고치지 않는다. 다만 새 알람이 생기고 `background.ts`의 알람 리스너를 이름으로 나누므로 단비 님 확인이 필요하다.

## 17. 확정 사항과 실행 계획 (2026-11-13, 리드 세션 전달용)

### 17-1. 동균 님 결정

| 항목 | 결정 |
|---|---|
| 수집 범위 | 범위를 좁히지 않는다. **수집 방법을 하나 더한다.** 화면 수집(지금 경로)은 그대로 모든 대화에서 동작한다. 이번에 만드는 동기화는 **"프로젝트만 수집" 방법**이다. 팝업에서 고른 ChatGPT 프로젝트의 대화만 동기화한다(기본 목록은 읽지 않는다). "계정 전체 동기화"는 지금 없으므로 다음 단계로 둔다. 16장 기능 B는 이 뜻으로 바꾼다. 화면 경로에 프로젝트 거름은 넣지 않는다 |
| 추천 기능 | 확장 조사에서 추천한 4개(A 화면 구조 변경 감지, C 새 후보 알림, D 팀 기록 불러오기, 그리고 "대화별 제외")를 넣는다. "대화별 제외"는 위 "프로젝트만 수집"으로 대신한다. 회의록의 E(싱크 맞추기 + 주기 설정 제거)도 넣는다 |
| 기준 버전 | 확장 0.2.7(`6342111`). 이 위에 갈래 브랜치를 만든다. 0.2.7에 이미 있는 것은 다시 만들지 않는다: 안내 문구 거르기, 2026-11 화면 구조 대응(`data-chatgpt-search-*`), 수집이 꺼져 있을 때 수동 보내기 차단(`sendBlockedReason`), 기본 검토함 주소 `syncup-live-murex.vercel.app`, 웹 '/collect 지금 수집하기' |
| 다른 조사 항목 | 위에 적은 것 말고는 넣지 않는다 |

### 17-2. 0.2.7 기준으로 달라지는 것

- **3층 패스는 "프로젝트 목록"만 읽는다.** 커서·쪽 넘기기는 `/backend-api/gizmos/{gizmo}/conversations?cursor=`로 한다(문자열 cursor). 기본 목록(`/conversations?order=updated`)은 이번 범위에서 쓰지 않는다. 프로젝트 고르기 화면은 `/backend-api/gizmos/snorlax/sidebar`로 프로젝트 이름 목록을 받는다(탭 클라이언트).
- **화면 경로의 메시지 id.** 0.2.7은 `data-chatgpt-search-message-ids` 목록의 첫 id를 쓴다. 한 답변이 노드 여러 개면 화면 id와 동기화 id가 다를 수 있다. 그래서 C4-b(화면이 이미 받은 턴은 건너뜀)를 꼭 넣는다. P3에서 새 속성까지 확인한다.
- **싱크 맞추기(E).** 팝업의 '지금 분류하기'와 웹 `/collect`의 '지금 수집하기'가 이미 `sendBlockedReason`·수집 중 판정을 공유한다. 싱크 맞추기는 이 버튼들을 바꿔 "프로젝트 동기화 패스 즉시 실행 + `collection.flush`"로 만든다.
  - 검토함 진입 시 자동 맞추기는 웹 → 확장 브리지 메시지(`shared/bridge.ts`)를 새로 둔다.
  - 이 메시지가 잘못 쓰이지 않게, 확장은 신뢰한 웹 주소에서 온 요청만 받는다(`web-url.ts`의 `isTrustedWebOrigin`).
- **파일 경로.** 수집기 변경 C1~C9의 위치는 `collector/` 아래, 시험은 `checks/` 아래다.
