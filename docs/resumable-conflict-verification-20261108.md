# 결정 충돌 검사: 진행 저장과 재개

기준은 `fed9646`이며 별도 브랜치 `codex/resumable-conflict-checks-20261108`에서 구현했다. backend 이력, 승인·개인정보 처리·로컬 모델 설정은 변경하지 않았다.

## 이전과 이후

| 항목 | 이전 | 이번 구현 |
|---|---|---|
| 기존 결정 30개 초과 | 전체 검사 실패 | 모든 후보 ID 저장, 실행당 최대 30쌍 처리 후 자동 계속 |
| 도중 실패 | 전체 비교 재실행 | 커밋한 쌍은 보존, 실패한 쌍부터 재시도 |
| 프로세스 종료 | 수동 재시도 | 진행 기록 있는 작업은 임대 만료 후 재개 |
| 진행 표시 | 상태·오류 안내 | 비교 완료 수/전체 수, 비활성 제외 수, 남은 검사 재시도 |
| 부분 충돌 발견 | 전체 성공 뒤 반영 | 성공한 쌍의 충돌을 즉시 반영, 전체 상태는 미완료 유지 |
| 기존 검토 중 결정 | 후속 비교에서 제외 | active와 review 모두 비교, superseded/rejected만 제외 |

유사도는 순서만 정한다. 후보를 잘라내거나 일부 결과를 전체 완료로 표시하지 않는다. 비교 결과와 커서는 같은 DB 트랜잭션으로 저장하며, 늦게 도착한 이전 작업 결과는 임대 식별값으로 차단한다. 응답에서 해당 쌍의 판정이 누락되면 커서를 전진시키지 않는다.

승인된 카드는 불변이므로 같은 작업의 완료한 쌍을 재사용한다. 판정 코드·프롬프트·모델 설정 해시가 바뀌면 진행 중 작업을 처음부터 재검사한다. 이전에 표시한 충돌은 자동 삭제하지 않는다. 완료된 과거 작업을 모두 재평가하는 기능은 추가하지 않았다.

기존 `diagnostics`는 마지막 쌍의 시도·호출 결과를 기록한다. 전체 진행 건수는 새 `progress`와 보드의 `conflictCheckProgress`를 사용한다. 시도 횟수는 한 쌍이 성공하면 다음 쌍에서 초기화된다.

## 직접 확인한 결과

- 실제 임시 PostgreSQL 17.9, 제한된 API 계정과 RLS에서 새 시나리오 7개 통과.
- 기존 결정 65개: 직접 실행 한 번에서 30개 커밋 후, 추가 HTTP 요청 없이 worker가 65개 전체 완료. 고유 쌍 65개, 마지막의 다른 주제 후보도 비교·충돌 표시.
- 35개 중 8번째 쌍 실패: 7개 결과와 부분 충돌 유지. 수동 재시도 후 35개 완료, 총 호출 36회(실패 1회 포함), 먼저 성공한 7쌍 재호출 없음.
- 실제 팀 API 별도 프로세스를 강제 종료하고 재시작: DB 커밋 완료한 쌍은 재호출하지 않고 35개 완료. 테스트 시간을 줄이기 위해 3분 임대 만료 시각만 DB에서 앞당겼다. 강제 종료 시 아직 커밋되지 않은 요청은 재실행될 수 있다.
- 검토 중 결정 포함, 중간에 비활성화된 결정 별도 집계, 팀 권한 회수 시 중단, 다른 팀의 진행 정보 접근 차단.
- 진행 열이 없는 DB의 시작 거절, 마이그레이션 2회 적용과 승인 기록 보존, 일시 DB 연결 오류 뒤 추가 요청 없는 자동 복구.
- 브라우저: 실제 Next/로컬 RPC/팀 HTTP API/임시 PostgreSQL에서 7/40 확인 필요 → 남은 검사 재시도 → 새로고침 후 12/40 → 25/40 → 40/40 완료. 다른 주제인 마지막 후보의 충돌도 화면 표시. 총 HTTP 모델 요청 41회(불확실 응답 1회 포함), 고유 쌍 40개.
- 최종 웹 생산 빌드 및 TypeScript 검사 통과. 마스킹·로컬 개인정보·승인 파이프라인과 쌍별 통신 재시도 묶음 42개 통과.
- AI 회귀 54개는 52개 즉시 통과, 샌드박스의 로컬 소켓 제한으로 실행하지 못한 2개는 허용된 환경에서 재실행하여 통과했다.
- 기존 팀 API·복구·진단·DB 업그레이드 197개 실행에서 190개 통과. 나머지 7개는 같은 재시도 횟수 기대값(`complete,2`)이 상속으로 중복 실행된 실패였다. 이제 쌍마다 시도 횟수를 초기화하므로 마지막 쌍의 `complete,1`과 전체 `2/2` 완료를 확인하도록 수정했다. 영향을 받는 네 클래스에서 해당 검사를 각각 재실행해 모두 통과했다. 197개 전체를 다시 반복하지는 않았다.

브라우저 증거: [결과 JSON](resumable-conflict-qa/verified-result.json), [진행 화면](resumable-conflict-qa/progress.jpg), [완료 화면](resumable-conflict-qa/completed.jpg). 모두 합성 데이터다. API 검사는 `python -m unittest check_resumable_conflicts`로 실행한다. 해당 검사는 자기 임시 Docker DB를 만들고 정리한다.

## 적용 방법과 한계

1. 관리자용 환경에서 `team_admin.py migrate-integration`을 실행해 `conflict_checks.progress` 열을 추가한다. 기존 RLS·승인 데이터는 유지된다. 앱 서비스에는 관리자 DB 자격증명을 전달하지 않는다.
2. 새 팀 API를 시작한다. 인증된 팀 요청이 worker를 시작하며 이후에는 추가 요청 없이 대기·재시도를 이어간다.
3. 서버 프로세스 전체 재시작 뒤에는 인증된 팀 요청이 한 번 필요하다. 인증 토큰은 메모리에만 있으며 DB 저장이나 RLS 우회 서비스 계정은 추가하지 않았다. 만료·회수된 인증으로는 재개하지 않는다.

진행 기록 없는 이전 버전의 실패·중단 건은 기존 수동 재시도를 유지한다. 불확실한 AI 판정은 자동 반복하지 않고 확인 필요로 둔다. 일시 통신 오류의 자동 재시도는 쌍마다 최초 시도 포함 3회다.

동기 AI CLI 자체의 30개·입력 크기·시간 제한은 유지한다. 팀 API는 한 쌍씩 호출하므로 전체 후보 수 한도에 걸리지 않는다. 대규모 부하·실제 외부 AI 비용/속도·판정 정확도는 이번에 측정하지 않았다. API/브라우저 모델은 제어 가능한 합성 HTTP Decisions 응답이며, 실제 OpenAI 평가나 운영 클라우드 검증이 아니다.

병렬 모델 호출과 여러 쌍을 한 요청으로 묶기는 구현하지 않았다. 완료 비교 재사용과 진행 저장으로 중복 비용부터 줄이는 최소 변경이다. 모델 자체의 오판은 이 구조로 방지할 수 없다.
