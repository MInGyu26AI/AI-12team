# 싱크업 결정 충돌 판정 규칙 (2차 케이스 요청)

싱크업은 팀원들이 각자 AI와 나눈 대화에서 팀 결정을 모으고, 새로 승인된 결정이 기존 결정과 어긋나면 알림을 띄운다.
이 문서는 충돌 판정기의 규칙이다. 함께 올린 분류 기준표(classification.md)는 어떤 문장이 '결정'이 되는지의 기준이다.

## 1. 입력과 출력

입력: 기존 결정 1개와 새 결정 1개. 결정마다 다음 필드가 있다.

| 필드 | 뜻 | 예 |
|---|---|---|
| content | 정리된 결정 한 줄 | 브라우저 확장 = MVP 포함 |
| sentence | 원문 문장 | 브라우저 확장도 MVP에 넣는 걸로 하자. |
| owner | 결정한 사람 | 이서준 |
| topic_key | 세부 주제 | MVP 범위 |
| 날짜 | 승인된 시각 | 2026-11-06 21:10 |

출력: 판정 하나와 확신도(0~1).

```json
{"judgement": "같음|변경|충돌|무관", "reason": "한 줄", "confidence": 0.85}
```

## 2. 판정 4가지

| 판정 | 뜻 | 알림 |
|---|---|---|
| 같음 | 같은 대상의 최종 값이 같다. 표현 차이, 기존 범위를 없애지 않는 구체화도 같음 | 없음 |
| 변경 | 같은 사람이 기존 결정을 고치거나, 팀 합의("회의에서", "다들", "합의")로 바꾼다 | 변경 알림 (파랑) |
| 충돌 | 겹치는 범위에서 두 값이 함께 성립할 수 없고, 다른 사람이 합의 없이 정했다 | 충돌 알림 (빨강) |
| 무관 | 대상·범위가 달라 두 결정이 함께 성립한다 | 없음 |

- **확인 필요**: 판정과 상관없이 확신도가 0.6 미만이면 서비스는 '확인 필요'(노랑)로 남기고 사람이 정하게 한다. 애매한 쌍은 확신도를 낮게 써야 한다.
- 판정 순서: 대상이 같은지 먼저 본다 → 최종 값이 같은지 → 같은 사람인지 / 팀 합의인지.
- topic_key 가 같아도 대상이 다르면 무관, topic_key 가 달라도 대상이 같으면 비교한다.
- 같은 단어가 있어도 대상이 다르면 무관. 예: "모바일 앱 = 행사 이후" / "앱 아이콘 = 둥근 사각형"

## 3. 예외 상황 10가지

이번에는 알림이 떠야 하는 경우(충돌·변경·확인 필요)를 더 많이 만든다. 아래 '이번 개수'를 따른다. 이름·주제·숫자는 다양하게
바꾸고, 팀 유형(수업 팀플 / 공모전 / 해커톤)도 섞는다. 지난번 케이스와 같은 이름·주제·문장은 쓰지 않는다.

| # | 이번 개수 |
|---|---|
| 1 정당한 변경 | 10 |
| 2 같은 대상, 다른 주제 이름 | 8 |
| 3 범위가 다른 결정 | 5 |
| 4 조건부 결정 | 8 |
| 5 숫자·날짜만 다름 | 10 |
| 6 부정 표현 | 8 |
| 7 제안과 결정 | 4 |
| 8 외부 조건 위반 | 8 |
| 9 여러 사람 연쇄 결정 | 6 |
| 10 농담·가정 | 3 |
| 11 자리·역할 바꾸기 (발표자·사회자·팀장) | 6 |

11번은 분류 기준표 v2 에서 생긴 유형이다. "발표는 유나가 하자" 다음에 다른 사람이 "발표는 내가 할게" → 충돌,
같은 사람이 "발표는 서준이한테 넘길게" → 변경.

| # | 예외 유형 | 기존 결정 | 새 결정 | 기대 판정 |
|---|---|---|---|---|
| 1 | 정당한 변경 | 박지민: 분석은 회귀분석으로 하자 | 박지민(다음 날): 분석은 군집분석으로 바꾸자 | 변경 |
| 2 | 같은 대상, 다른 주제 이름 | 박지민 [MVP 범위]: 확장 제외 | 이서준 [기능 범위]: 확장도 넣자 | 충돌 |
| 3 | 범위가 다른 결정 | 발표는 유나가 하자 | PPT 제작은 서준이가 하자 | 무관 |
| 4 | 조건부 결정 | 시간 남으면 Claude도 지원하자 | ChatGPT만 지원하자 | 확인 필요 (확신도 0.6 미만) |
| 5 | 숫자·날짜만 다름 | 박지민: 마감은 금요일 | 이서준: 마감은 토요일 | 충돌 (같은 사람이면 변경) |
| 6 | 부정 표현 | 박지민: 로그인 기능 넣자 | 이서준: 로그인은 빼자 | 충돌 |
| 7 | 제안과 결정 | 주제를 바꾸면 어때? (제안) | 주제는 청년 주거로 확정 | 알림 없음 (제안은 결정이 아니라 비교하지 않음. 쌍으로 들어오면 무관) |
| 8 | 외부 조건 위반 | 교수님: 보고서는 10쪽 이내 | 팀: 보고서는 15쪽으로 쓰자 | 충돌 |
| 9 | 여러 사람 연쇄 결정 | A → B 로 바뀐 현재 결정 B | C가 다시 정함 | 현재 결정(B)과 비교. 이미 바뀐 A와는 비교하지 않음 |
| 10 | 농담·가정 | 주제는 청년 주거로 확정 | 차라리 주제를 통째로 바꿔버릴까 ㅋㅋ | 알림 없음 (결정이 아님. 쌍으로 들어오면 무관) |

## 4. 알림을 띄우면 안 되는 경우

각 유형 안에 아래 경우를 2개 이상씩 넣는다. 잘못 띄운 알림은 팀원이 알림을 무시하게 만든다.

- 같은 결정을 다른 사람이 다시 전함: 박지민 "서비스명은 싱크업" / 이서준 "지민이가 정한 싱크업으로 가기로 했어" → 같음
- 요청 속 전제로 같은 결정을 말함: "MySQL 기준으로 테이블 짜 줘" → 같음
- 기존 범위를 없애지 않는 구체화: "발표 10분" / "발표 10분 중 데모 3분" → 같음
- 이름만 비슷한 다른 대상: "팀 이름 = 북극성" / "북극성 로고 색 = 남색" → 무관
- 개인 사정이 섞인 문장: "수요일 병원 가서 회의 못 가" → 개인 문장이라 결정이 아님, 비교하지 않음

## 5. 케이스에 넣어 줄 것

**상황 설명(Situation)에는 두 결정의 원문 문장을 한국어 그대로 큰따옴표 안에 넣고, 바로 뒤 괄호에 결정자 이름과 날짜를 적는다.**
예: 기존 결정 "브라우저 확장은 행사 끝나고 하자." (박지민, 2026-11-06 19:50), 새 결정 "브라우저 확장도 MVP에 넣자." (이서준, 2026-11-06 21:10)
연쇄 결정(9번)은 세 문장 모두 이렇게 적는다. 팀 합의 표현("회의에서", "다들")이 있으면 원문에 그대로 둔다.

케이스마다 다음을 적는다.

- 유형 번호(1~10), 팀 유형
- 기존 결정, 새 결정 (각각 content, sentence, owner, topic_key, 날짜)
- 기대 판정 (같음 / 변경 / 충돌 / 무관 / 확인 필요 / 알림 없음)
- 기대 알림 (없음 / 변경 알림 / 충돌 알림 / 확인 필요)
- 판정 이유 한 줄
